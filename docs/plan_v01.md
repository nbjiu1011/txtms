# TX TMS 전체 개발 기획

## 1. 서비스 목적

TX TMS는 고객사의 메시지 및 콘텐츠를 **작성 → 검수자 배정 → 검수 → 선택적 승인 → 완료 → 검색·보관**하는 협업 시스템이다.

콘텐츠 유형은 다음 4종을 지원한다.

- 알림톡
- 문자
- RCS
- 자유입력형

알림톡·문자·RCS의 실제 외부 발송 기능은 본 시스템의 목적이 아니다. 채널별 문안을 작성하고 검수하기 위한 입력 규칙, 글자 수/바이트 안내 및 목업을 제공한다.

---

# 2. 관리 구조

```text
고객사
 └─ 프로젝트
     └─ 요청
         ├─ 콘텐츠 1
         ├─ 콘텐츠 2
         └─ 콘텐츠 N
```

### 고객사
최상위 데이터 및 권한 경계.

### 프로젝트
실제 업무 참여자·역할·권한·요청·변수·공지를 묶는 업무 단위.

### 요청
하나의 목적과 납기를 가진 업무 단위이며 콘텐츠를 1개 이상 포함한다.

요청에서 관리:

- 상태
- 검수 차수
- 검수자 배정
- 주담당 검수자
- 완료 여부
- 납기
- 긴급도

### 콘텐츠

실제 검수 대상 문안 또는 파일.

콘텐츠에서 관리:

- 문안
- 변수
- 버튼/연결값
- 첨부파일
- 콘텐츠 버전
- 변경 이력

**콘텐츠별 업무 상태는 두지 않는다. 모든 콘텐츠는 상위 요청의 상태를 따른다.**

---

# 3. 사용자 역할

총 6개 역할을 사용한다.

### 요청자
- 요청 작성
- 콘텐츠 작성
- 검수 요청
- 배정 전 요청 취소
- 검수 시작 후 회수 요청
- 확인 요청 답변
- 완료 결과 조회

### 검수자
- 배정된 요청 검수
- 문안/파일 수정
- 검수 의견
- 확인 요청
- 텍스트 교정 실행

### 대표 검수자
- 배정 대기 요청 관리
- 검수자 1명 이상 배정
- 주담당 검수자 1명 지정
- 검수자 변경 및 인수인계
- 검수 현황/업무량 확인
- 확정 납기·긴급도 관리

### 주담당 검수자

별도 역할이 아니라 배정된 검수자 중 대표 검수자가 지정한 1명이다.

주담당만:

- 회수 승인/거절
- 요청 단위 검수 완료

를 처리할 수 있다.

### 승인자
승인 기능을 사용하는 고객사에서만 동작한다.

- 승인 대기 목록 조회
- 최종 승인
- 수정 요청
- 승인 대기 중 납기/긴급도 변경

### 고객사 관리자
- 프로젝트 관리
- 사용자 초대/비활성
- 역할 및 프로젝트 권한
- 변수 관리
- 고객사 설정
- 공지
- 실적 조회
- 인수인계

### 솔루션 운영 담당자
- 고객사 생성/비활성
- 콘텐츠 유형 활성화
- 초기 설정
- 시드 데이터
- 고객사 × 콘텐츠 유형별 교정 데이터셋 배정

고객사의 실제 콘텐츠를 자동으로 열람할 수 없다.

---

# 4. 권한 원칙

권한은 반드시:

**사용자 역할 + 고객사 + 프로젝트 + 현재 요청 상태**

를 함께 판단한다.

화면에서 버튼을 숨기는 것만으로 권한을 처리해서는 안 된다.

동일한 권한 검증을:

- 화면
- 직접 URL 접근
- API
- 첨부파일
- 다운로드
- 검색
- 알림 이동

전체에 적용한다.

작성 중 요청은 작성자만 조회할 수 있다.

취소 또는 회수되어 다시 작성 중이 된 요청 역시 작성자만 조회한다.

고객사 관리자는 자신의 고객사 전체 프로젝트에 접근할 수 있다.

같은 프로젝트에서 한 사용자가 요청자와 검수자를 동시에 맡을 수 없다.

---

# 5. 로그인 및 계정

Phase 1은 이메일 + 비밀번호 자체 로그인이다.

### 가입 Flow

```text
고객사 관리자
 ↓
사용자 이메일 초대
 ↓
초대 메일
 ↓
사용자가 링크 접속
 ↓
비밀번호 설정
 ↓
계정 활성화
 ↓
로그인
```

초대 링크 유효기간: 7일.

재발급하면 기존 링크는 무효화한다.

회사 도메인이 아닌 이메일도 초대할 수 있지만 관리자에게 경고한다.

비밀번호는 8자 이상이며 영문·숫자·특수문자 중 2종 이상을 포함한다.

비밀번호 재설정 링크는 1시간 유효하다.

30분간 활동이 없으면 세션을 종료한다.

'로그인 유지' 사용 시 최대 14일 유지하며 30분 만료를 적용하지 않는다.

본인은 이름·소속만 수정한다.

이메일·역할·권한은 고객사 관리자가 관리한다.

---

# 6. 핵심 요청 상태

```text
작성 중
 ↓
배정 대기
 ↓
검수 중
 ↕
확인 요청
 ↓
[승인 미사용]
검수 완료

또는

검수 중
 ↓
[승인 사용]
승인 대기
 ↓
승인 완료
```

최종 완료 상태:

- 승인 미사용 → 검수 완료
- 승인 사용 → 승인 완료

승인 사용 여부는 고객사 도입 시 결정하고 운영 중 변경하지 않는다.

---

# 7. 요청 작성 Flow

```text
새 요청
 ↓
공통 정보 입력
 ↓
콘텐츠 유형 선택
 ↓
콘텐츠 작성
 ↓
자동/수동 저장
 ↓
필요 시 변수 삽입
 ↓
필요 시 텍스트 교정
 ↓
필수값 검증
 ↓
검수 요청
 ↓
배정 대기
```

공통 필수값:

- 제목
- 유형
- 희망 납기
- 목적
- 대상 고객
- 배경

캠페인은 선택값이다.

활성화된 콘텐츠 유형만 선택할 수 있다.

---

# 8. 저장

자동 저장과 수동 저장을 모두 제공한다.

자동 저장:

- 30초 간격
- 사용자가 입력을 멈춘 시점

저장 실패 시 3회 재시도한다.

화면에서는:

- 저장 중
- 저장됨
- 저장 실패

상태를 구분한다.

반복 저장/제출로 요청이나 검수 차수가 중복 생성되어서는 안 된다.

기존 요청을 복제하면 별도의 새로운 `작성 중` 요청을 생성한다.

---

# 9. 콘텐츠 유형

## 알림톡
- 승인 템플릿
- 본문
- 변수
- 버튼
- 텍스트 교정
- 목업
- XLSX 대량 등록

1차 기준:

- 본문 1,000자
- 버튼 최대 5개
- 버튼명 14자

## 문자
- 발신자
- 본문
- 고객센터/수신거부 안내 여부
- 텍스트 교정
- 목업
- XLSX 대량 등록

1차 기준:

- SMS 90바이트
- LMS 2,000바이트

실제 SMS/LMS 발송 기능은 제공하지 않는다.

SMS 기준 초과 시 LMS 기준에 해당한다는 작성 안내만 제공한다.

## RCS
- 제목
- 본문
- 이미지
- 이미지 설명
- 카드 수
- 버튼
- 텍스트 교정
- 목업

세부 길이 기준은 별도 확정한다.

## 자유입력형
- 직접 입력 텍스트
- 변수
- 선택 제목
- 첨부파일

첨부파일이 존재하면 텍스트 교정을 사용할 수 없다.

---

# 10. 첨부파일

지원 형식:

- PDF
- DOCX
- HWP
- XLSX
- PPTX
- TXT
- PNG
- JPG

개발 제안 기준:

- 요청당 최대 10개
- 파일당 최대 20MB
- 요청당 총 최대 100MB

업로드 Flow:

```text
파일 선택
 ↓
개수/용량 검사
 ↓
확장자 검사
 ↓
실제 MIME 검사
 ↓
바이러스 검사
 ↓
정상 → 첨부 등록
위험/검사 실패 → 등록 차단
```

파일마다 전체 분량과 실제 검수 범위를 입력한다.

- PDF/Word/HWP → 페이지
- Excel → 행
- PPT → 슬라이드
- TXT → 줄
- 이미지 → 장

업무량에는 파일 개수가 아니라 실제 검수 범위를 사용한다.

---

# 11. XLSX 대량 등록

알림톡과 문자에 제공한다.

### 알림톡
- 승인 템플릿
- 본문
- 버튼명
- 버튼 링크

### 문자
- 발신자
- 본문
- 수신거부문구 포함 Y/N

기본 최대 1,000행.

처리 Flow:

```text
XLSX 업로드
 ↓
파일 구조 확인
 ↓
행별 파싱
 ↓
행별 유효성 검사
 ↓
 ┌ 정상 → 반영
 └ 오류 → 제외 + 사유 표시
```

한 행의 오류 때문에 전체 파일을 실패시키지 않는다.

---

# 12. 변수

변수는 프로젝트 단위 공유 데이터다.

사용자가 변수명을 문안에 임의 입력하는 방식이 아니라 검색 후 선택하여 삽입한다.

변수 키:

- 영문 소문자
- 숫자
- `_`
- 공백 불가
- 대소문자 구분 없이 프로젝트 내 중복 불가

자료형:

- 텍스트
- 정수/소수
- 날짜 YYYY-MM-DD
- HTTP/HTTPS 링크

문안에서 사용 중인 변수는 키 변경/삭제 불가.

값 변경:

- 진행 중 문안 → 변경값 반영
- 완료 문안 → 완료 당시 값 유지

---

# 13. 텍스트 교정

AI 교정이 아니다.

와이어링크에서 제공하는 **문자열 + 정규표현식 기반 교정 규칙**을 사용한다.

명세: DOCX  
샘플/규칙 데이터: XLSX

실제 정규표현식 Flavor는 백엔드 교정 엔진의 언어에 맞춰 확정한다.

Flow:

```text
문안 작성
 ↓
텍스트 교정 실행
 ↓
고객사 + 콘텐츠 유형 확인
 ↓
해당 유효 데이터셋 조회
 ↓
문자열/정규표현식 매칭
 ↓
검출 결과 생성
 ↓
문안별 결과 카드
 ↓
결과 선택
 ↓
해당 문자열 위치 이동
```

교정 실행은 선택 사항이다.

**교정을 실행하지 않아도 검수 요청/검수 완료 가능하다.**

다건 요청은 전체 검사를 지원한다.

문안·변수·연결값이 변경되면 기존 결과를:

`최신 내용과 불일치`

상태로 표시한다.

자유입력형에 첨부가 하나라도 있으면:

- 교정 버튼 비활성
- 결과 영역 비활성
- 전체 검사 제외

첨부를 모두 삭제하면 다시 활성화한다.

---

# 14. 검수 요청

제출 시 유형별 필수값과 연결값을 검증한다.

교정 실행 여부는 제출 조건이 아니다.

정상:

```text
작성 중
 ↓
서버 저장
 ↓
배정 대기
```

배정 대기에서는 요청자가 즉시 취소할 수 있다.

```text
배정 대기
 ↓ 취소
작성 중
```

취소 이력은 남긴다.

검수 차수는 증가하지 않는다.

---

# 15. 검수자 배정

대표 검수자가 처리한다.

```text
배정 대기
 ↓
검수자 1명 이상 선택
 ↓
주담당 1명 지정
 ↓
검수 중
```

검수 중에는 사유와 인수인계를 남긴 뒤 검수자/주담당 변경이 가능하다.

변경 불가:

- 확인 요청
- 승인 대기
- 검수 완료
- 승인 완료

---

# 16. 검수

배정된 검수자는 `검수 중`에서만 편집한다.

가능 기능:

- 문안 편집
- 파일 수정본 등록
- 검수 의견
- 텍스트 교정
- 확인 요청

문안에는 편집 잠금을 적용한다.

30분 동안 입력이 없으면 잠금 자동 해제.

대표 검수자/고객사 관리자는 강제 해제할 수 있으며 이력을 남긴다.

동시에 수정하여 오래된 내용이 최신 내용을 덮어쓰지 않도록 저장 버전을 비교한다.

파일 수정은 기존 파일을 덮어쓰지 않고 새 버전으로 등록한다.

---

# 17. 확인 요청 Flow

검수자가 요청자에게 질문해야 할 경우:

```text
검수 중
 ↓
확인 요청
 ↓
요청 전체 검수 일시 중단
 ↓
요청자 답변
 ↓
문안 수정 여부?
 ├─ NO → 검수 중 / 차수 유지
 └─ YES → 검수 중 / 검수 차수 +1
```

한 검수 차수에서 확인 요청은 여러 번 반복할 수 있다.

질문·답변·대상 콘텐츠를 모두 업무 이력에 남긴다.

---

# 18. 회수 요청 Flow

검수자가 배정된 후 요청자는 직접 취소할 수 없다.

```text
검수 중
 ↓
요청자 회수 요청
 ↓
상태는 '검수 중' 유지
+ '회수 요청됨' 표시
 ↓
주담당 판단
 ├─ 승인
 │   ↓
 │ 작성 중
 │ 배정 해제
 │
 └─ 거절
     ↓
   검수 중 유지
```

회수 요청 중 요청자는 편집할 수 없다.

회수는 `확인 요청`, `승인 대기`에서는 처리할 수 없다.

회수 승인 후 다시 검수 요청하면 검수 차수 +1.

---

# 19. 검수 완료

주담당 검수자만 실행한다.

```text
공동 검수 결과 확인
 ↓
최종 대상 버전 확인
 ↓
검수 완료
 ↓
고객사 승인 사용?
```

### 승인 미사용

```text
검수 완료
 ↓
최종 완료
```

### 승인 사용

```text
검수 완료 처리
 ↓
승인 대기
```

# 20. 승인 Flow

프로젝트에는 승인자가 1명 이상 존재해야 한다.

승인 대기 요청은 프로젝트 승인자 공용 큐에서 처리한다.

승인자 전원의 동의는 필요하지 않다.

적격 승인자 한 명의 처리로 완료된다.

단, 해당 요청의:

- 요청자
- 배정 검수자
- 주담당 검수자

는 승인자 역할도 가지고 있더라도 해당 요청을 승인할 수 없다.

### 적격 승인자 없음

```text
검수 완료 시도
 ↓
적격 승인자 확인
 ↓
없음
 ↓
승인 대기 전환 차단
 ↓
고객사 관리자 → 승인자 지정 요청
요청자/대표 검수자 → 지연 알림
```

임시 승인 위임은 없다.

---

# 21. 승인 결과

```text
승인 대기
 ↓
승인자 검토
 ↓
 ┌ 승인
 │  ↓
 │ 승인 완료
 │
 └ 수정 요청
    ↓
   이유/위치/기대내용 기록
    ↓
   검수 차수 +1
    ↓
   검수 중
    ↓
   기존 검수자 재검수
    ↓
   다시 승인 대기
```

승인 대기에서는 콘텐츠 버전·검수자·주담당을 고정한다.

이 상태에서는 승인자만 확정 납기·긴급도를 변경할 수 있다.

# 22. 검수 차수 규칙

### 차수 유지
- 확인 요청 자체
- 설명만 포함한 확인 응답
- 검수자의 문안/파일 수정
- 배정 전 취소 후 재요청

### +1
- 확인 응답 중 요청자가 문안 수정
- 회수 승인 후 재요청
- 승인자의 수정 요청

**콘텐츠 버전 증가와 검수 차수 증가는 서로 다른 개념이다.**

# 23. 완료 결과

최종 완료 시 `완료 묶음`을 고정한다.

포함:

- 완료 콘텐츠
- 완료 버전
- 완료 상태
- 완료 시각

승인 미사용 → 검수 완료본이 원본.

승인 사용 → 승인 완료본이 원본.

완료 원본을 직접 수정하지 않는다.

수정이 필요하면 원본과 연결된 새로운 `작성 중` 요청을 생성한다.

# 27. 납기 및 긴급도

요청자의 희망 납기는 원본 그대로 보존한다.

별도로:

- 확정 납기
- 긴급도

를 관리한다.

Phase 1 변경 가능:

- 고객사 관리자
- 대표 검수자
- 승인자

단 `승인 대기`에서는 승인자만 변경할 수 있다.

최종 완료 이후 변경 불가.

모든 변경에:

- 변경자
- 사유
- 이전 값
- 새 값
- 시각

을 기록한다.

# 28. 업무량

대표 검수자가 확인:

- 배정 대기
- 검수 중
- 확인 요청
- 승인 대기
- 납기 임박
- 지연
- 검수자별 업무량

문안 업무량은:

`본문 + 공백 + 줄바꿈`

기준.

제목/버튼 제외.

변수는 치환 전 원문 기준.

파일은 실제 검수 범위를 사용하며 페이지·행·슬라이드 등 서로 다른 단위를 임의 합산하지 않는다.

# 29. 실적

완료율:

`조회 기간 접수 요청 중 현재까지 완료된 요청 ÷ 조회 기간 접수 요청`

취소 요청 제외.

회수 후 재요청은 같은 요청 1건으로 계산한다.

분모 0 → `–`.

기간은 접수일 기준 KST 00:00이며 종료일을 포함한다.

# 31. 알림

행동을 수행한 본인은 알림 대상에서 제외한다.

다음 행동 담당자에게 중복 없이 알린다.

주요 이벤트:

- 확인 요청

- 승인 대기

- 수정 요청
- 납기 변경

알림의 `읽음`과 실제 `업무 완료`는 별도 상태다.

알림에서 요청으로 이동할 때 권한을 다시 검사한다.

# 32. 재통지

미처리 또는 납기 임박일 때만 재통지한다.

최초 알림 후 24시간 간격, 최대 3회.

1~2회:
- 제품 내 알림

3회:
- 제품 내 알림
- 이메일

일반 미처리 재통지는 제품 내 알림만 사용한다.

업무 처리 → 재통지 중단.

납기 변경 → 재통지 회차 초기화.

미처리와 납기 임박이 동시에 해당하면 납기 임박 재통지 하나만 발생한다.

# 34. 제품 내부 멀티탭

최대 10개.

- 입력 내용

- 필터

상태를 유지한다.

미저장 변경이 있으면 탭 종료 전 경고한다.

교정 결과가 다른 탭에 있으면 해당 탭으로 이동하고 검출 문자열 위치로 이동한다.

# 40. 구현 시 절대 유지해야 할 핵심 규칙

1. 상태는 요청 단위다.
2. 콘텐츠에는 별도 업무 상태를 두지 않는다.
3. 콘텐츠 버전과 검수 차수는 서로 다른 개념이다.
4. 작성 중 요청은 작성자만 볼 수 있다.
5. 배정 전에는 취소, 배정 후에는 회수다.
6. 회수 승인/거절은 주담당만 한다.
7. 검수 완료도 주담당만 한다.
8. 확인 요청은 요청 전체 검수를 중지한다.
9. 확인 답변에서 문안을 수정했을 때만 차수가 증가한다.
10. 승인 사용 여부에 따라 최종 완료 상태가 달라진다.
11. 요청에 참여한 요청자/검수자는 해당 요청을 승인할 수 없다.
12. 적격 승인자가 없으면 승인 대기로 넘어가지 않는다.
13. 승인 수정 요청은 기존 검수자에게 돌아가며 차수가 증가한다.
14. 완료 원본은 직접 수정하지 않고 후속 요청을 만든다.
15. 모든 주요 상태·권한·변경 행동은 이력으로 남긴다.
16. 화면에서 버튼을 숨기는 것과 별개로 서버에서 권한을 검증한다.
17. 텍스트 교정은 선택 기능이며 제출/완료 조건이 아니다.
18. 첨부파일이 있는 자유입력형은 텍스트 교정 대상이 아니다.
19. 실제 SMS/LMS 등 외부 메시지 발송은 본 시스템 범위가 아니다.
20. Phase 1과 Phase 2 기능을 혼합하지 않는다.
