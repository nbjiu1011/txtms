# TX TMS 전체 프로젝트 기획서

버전 1.0 · 작성일 2026년 10월 1일 · 백엔드와 데이터베이스 설계를 위한 개발 기준안

TX TMS는 고객 안내와 마케팅 콘텐츠의 작성, 검수, 선택적 승인, 최종본 보관을 관리하는 업무 시스템이다. 이번 개발의 목표는 화면 시연이 아니라 실제 계정과 데이터를 사용하는 운영 가능한 제품이다. 이 문서는 최신 클라이언트 요청을 업무 규칙, 권한, 데이터 관계, 처리 책임, 운영 범위로 정리한다.

현재 자료는 가견적과 세부 조건 협의를 위한 요청서다. **1차 90개 기능은 클라이언트의 현재 요청 분류이며, 양측의 최종 계약 합의를 뜻하지 않는다.** 협의사항 24건은 모두 미회신 상태다. 이 문서의 설계 제안으로 미합의 정책을 확정하거나 기능 범위를 늘리지 않는다.

## 2 제품 목적과 대상

### 2.1 해결할 문제

콘텐츠와 검수 의견이 서로 다른 경로에 흩어지면 최신 문안, 담당자, 승인 여부, 확정 납기를 확인하기 어렵다. TX TMS는 요청 목적부터 완료 결과까지 연결해 담당자와 책임을 명확히 하고, 변경·확인·승인 근거를 같은 업무 안에서 조회할 수 있게 한다.

### 2.2 주요 사용자

고객사의 CRM·마케팅·고객 소통 담당자가 콘텐츠를 작성한다. 검수 운영팀이 문안과 파일을 검토하고, 필요할 때 고객사 승인자가 최종 판단한다. 고객사 관리자는 조직과 프로젝트를 운영하며, 솔루션 운영 담당자는 고객사 초기 설정과 콘텐츠 유형·교정 기준을 운영한다.

### 2.3 제품 경계

TX TMS가 관리하는 범위는 작성, 검수, 선택적 승인, 완료 결과와 이력이다. 알림톡·문자·RCS를 실제 고객에게 발송하는 기능이나 외부 채널의 템플릿 등록·심사 대행은 현재 99개 기능의 요청 범위에 포함되어 있지 않다. 목업과 길이 검사는 외부 심사 통과나 발송 성공을 보장하지 않는다.

규칙 기반 교정은 표현 검토 보조 기능이다. 생성형 AI가 문안을 생성하거나 사실관계를 판단하는 기능으로 해석하지 않는다.

### 2.4 제품의 완료 기준

실제 사용자가 자신의 권한으로 로그인하고, 요청을 저장·제출하여 검수와 필요한 승인을 거친 뒤, 고정된 최종본과 처리 이력을 조회·반출할 수 있어야 한다. 다른 고객사나 권한 없는 프로젝트의 데이터는 목록, 검색, 파일, 알림을 통해서도 노출되지 않아야 한다. 사용자나 조직이 비활성화되더라도 과거 결과와 책임 기록은 유지되어야 한다.

## 4 조직과 업무 단위

| 단위 | 역할 | 주요 관리 정보 |
|---|---|---|
| 고객사 | 최상위 데이터와 운영 정책 경계 | 회사 정보, 사용 상태, 승인 사용 여부, 구성원, 운영 설정 |
| 프로젝트 | 협업과 조회 권한 경계 | 참여자, 역할, 대표 검수자, 승인자 그룹, 변수, 공지 |
| 요청 | 상태와 납기를 공유하는 업무 단위 | 제목·배경, 작성자, 상태, 검수 차수, 배정, 납기, 완료 연결 |
| 콘텐츠 | 개별 검수 대상 | 유형별 문안과 속성, 변수, 버튼, 파일, 저장 버전 |

하나의 고객사는 여러 프로젝트를, 하나의 프로젝트는 여러 요청을, 하나의 요청은 하나 이상의 콘텐츠를 포함한다. 콘텐츠는 독립적인 업무 상태를 갖지 않고 요청 상태를 따른다. 작성 도중 콘텐츠가 아직 없는 초안 저장을 허용할지는 추가 설계 결정이지만, 제출된 요청에는 검수 대상이 반드시 있어야 한다.

콘텐츠 버전은 저장 내용의 변화를, 검수 차수는 요청의 재검수 흐름을 의미한다. 두 값을 같은 번호로 관리하지 않는다. 완료 묶음은 최종 확정한 콘텐츠 버전과 파일 버전을 고정한다.

## 5 사용자와 권한

### 5.1 역할 모델

| 역할 | 기본 책임 | 제한 |
|---|---|---|
| 요청자 | 요청 작성·제출, 본인 요청 취소·회수 요청, 확인 응답 | 작성 중 또는 확인 응답 중인 본인 콘텐츠만 편집 |
| 검수자 | 배정된 요청 검수, 문안·파일 수정, 질문·의견 | 검수 중에만 작업. 요청 단위 완료와 회수 처리는 주담당만 |
| 대표 검수자 | 복수 검수자 배정, 주담당 지정, 인수인계, 업무량 관리 | 프로젝트별 역할. 배정 관리 권한과 직접 문안 편집 권한은 다름 |

| 솔루션 운영 담당자 | 고객사 생성·비활성, 초기 설정·시드, 유형·기준 연결 | 고객사 콘텐츠에 자동 접근 불가. 프로젝트와 접근 기간 별도 부여 |

주담당은 별도의 일곱 번째 사용자 역할이 아니라 요청에 배정된 검수자 중 한 명에게 부여하는 책임이다. 같은 사용자는 프로젝트별로 여러 역할을 가질 수 있지만, 같은 프로젝트에서 요청자와 검수자를 동시에 부여할 수 없다. 고객사 관리자와 솔루션 운영 담당자의 관리 권한 범위는 프로젝트 역할과 구분해 표현해야 한다.

### 5.2 조회 원칙

프로젝트 참여자는 해당 프로젝트의 제출된 모든 요청과 하위 콘텐츠를 조회할 수 있다. 특정 요청자와 검수자 사이만 보이게 할 업무는 별도 프로젝트로 나눈다. 고객사 관리자는 소속 고객사 전체 프로젝트에 접근한다.

**작성 중 요청은 작성한 요청자만 조회한다.** 배정 전 취소하거나 회수 승인으로 작성 중에 복귀한 요청에도 이 제한을 적용한다. 고객사 관리자 또는 과거 참여자가 예전 이력을 예외적으로 볼 수 있는지는 협의 18의 미정 항목이다. 별도 결정 없이 관리자 예외를 추가하지 않는다.

솔루션 운영 담당자의 지원 접근은 대상 프로젝트, 허용 기간, 허용 행위가 식별되어야 한다. 별도 접근 권한이 문안 수정이나 업무 승인까지 자동 부여한다는 뜻은 아니다. 수정 가능한 행위와 권한 부여 주체는 협의 18·22에서 확정하고, 조회·수정·내보내기 기록을 남긴다.

| 검수 완료 | 주담당 검수자 | 검수 중, 대상 버전과 공동 검수 결과 확인 |
| 최종 승인·수정 요청 | 적격 프로젝트 승인자 | 승인 대기 |
| 납기·긴급도 결정·변경 | 고객사 관리자·대표 검수자·승인자 | 최종 완료 전. 승인 대기에서는 승인자만 |
| 완료본 조회·복사·다운로드 | 조회 권한 보유자 | 최종 완료, 고객사·프로젝트 범위 확인 |
| 변수 신규 등록 | 권한 있는 프로젝트 사용자 | 프로젝트 고유 키와 자료형 검증 |
| 변수 목록·사용 상태 관리 | 고객사 관리자 | 소속 고객사 프로젝트 |
| 고객사·프로젝트 공지 관리 | 고객사 관리자 | 관리 가능한 범위 |
| 유형 활성·유효 데이터셋 배정 | 솔루션 운영 담당자 | 운영 권한 범위 |

### 5.4 서버 권한 판단 원칙

계정 활성 여부, 고객사와 프로젝트 범위, 관리 또는 업무 역할, 현재 요청 상태, 해당 요청에서의 작성자·배정자·주담당·승인 적격성, 임시 접근 기간을 함께 판단한다. 화면에서 버튼을 숨기는 것으로 권한 통제를 대신하지 않는다.

목록·상세뿐 아니라 검색 결과와 검색 개수, 대시보드 집계, 알림 제목·미리보기, 파일 원본, 다운로드, 통합 이력, 비동기 작업 결과에도 같은 범위를 적용한다. 역할이나 참여 범위가 바뀐 뒤에는 열려 있던 탭과 과거 알림에서도 재확인한다.

## 6 로그인과 계정 수명주기

이메일과 비밀번호를 이용한 자체 로그인이 1차다. 고객사 관리자가 이메일로 초대하고, 사용자가 초대 링크를 수락해 비밀번호를 설정한다. 비밀번호 제시 규칙은 8자 이상이며 영문·숫자·특수문자 중 두 종류 이상이다. 초대 유효기간, 재발급, 비밀번호 재설정, 실패 횟수와 제한 정책은 협의 후 정한다.

30분 미사용 시 세션 만료와 로그인 유지 옵션을 제공한다. 로그인 유지의 최대 기간, 미사용 만료와의 우선순위, 권한 변경 후 세션 재검증 방식은 협의 02에서 확정한다. 클라이언트 화면의 타이머만으로 만료를 처리하지 않고 서버에서 접속 상태를 판단한다.

사용자는 자신의 이름과 소속만 수정한다. 이메일·역할·권한은 고객사 관리자가 변경한다. 이메일 변경의 인증 절차와 이력은 협의 13에서 정한다. 한 계정의 복수 고객사 소속, 이메일 고유 범위, 고객사 이동 방식은 문서에 상세 정의가 없으므로 논리 모델 확정 전에 결정한다.

계정 비활성화, 역할 해제, 프로젝트 제외 전에는 진행 업무와 대체자를 확인한다. 과거 검수와 승인 이력의 실행자는 바꾸지 않는다. 이력이 있는 계정은 비활성 상태로 유지하며, 시연 계정과 실제 운영 계정·실적은 분리한다.

## 7 요청 상태와 전환

승인 미사용 고객사는 검수 완료가 최종 상태이고, 승인 사용 고객사는 승인 완료가 최종 상태다. 승인 사용 여부는 도입 시 고객사별로 정하며 운영 중 변경할 수 없다.

| 현재 상태 | 행동 | 실행자 | 다음 상태 | 처리 원칙 |
|---|---|---|---|---|
| 작성 중 | 검수 요청 제출 | 해당 요청자 | 배정 대기 | 필수값 검증과 서버 저장 후 전환 |
| 배정 대기 | 요청 취소 | 해당 요청자 | 작성 중 | 취소 이력 보존, 작성자 단독 조회 복귀 |
| 배정 대기 | 검수자 배정 | 대표 검수자 | 검수 중 | 검수자 1명 이상과 주담당 1명 지정 |
| 검수 중 | 확인 요청 | 배정 검수자 | 확인 요청 | 요청 전체 검수 일시 중단 |
| 확인 요청 | 답변 제출 | 해당 요청자 | 검수 중 | 문안 수정 포함 여부에 따라 차수 판단 |
| 검수 중 | 회수 신청 | 해당 요청자 | 검수 중 | 회수 요청됨 표시, 요청자 편집 불가 |
| 검수 중 | 회수 승인 | 주담당 | 작성 중 | 활성 배정 해제, 기존 배정 이력 보존 |
| 검수 중 | 회수 거절 | 주담당 | 검수 중 | 기존 배정 유지, 의견 기록 |
| 검수 중 | 검수 완료 | 주담당 | 검수 완료 | 승인 미사용 고객사, 완료 묶음 고정 |
| 검수 중 | 검수 완료 | 주담당 | 승인 대기 | 승인 사용 고객사, 승인 대상 버전 고정 |
| 승인 대기 | 최종 승인 | 적격 승인자 | 승인 완료 | 최종 완료 묶음 고정 |
| 승인 대기 | 수정 요청 | 적격 승인자 | 검수 중 | 기존 검수자·주담당 유지, 차수 증가 |
| 최종 완료 | 후속 요청 작성 | 요청 작성 권한자 | 별도 작성 중 요청 | 완료 원본은 유지하고 연결된 새 요청 생성 |

회수 신청은 독립적인 요청 상태가 아니다. 취소 완료·회수 완료 상태를 만들거나 취소·회수 시 별도 완료 원본을 생성하지 않는다. 확인 요청과 승인 대기 상태에서는 회수를 처리할 수 없다.

### 7.1 검수 차수

| 사건 | 차수 | 기록 기준 |
|---|---|---|
| 최초 검수 | 첫 차수 | 생성 시점과 표시 시점은 기술 설계에서 일관되게 정의 |
| 확인 요청 발송 | 유지 | 질문만으로 재검수 차수를 만들지 않음 |
| 문안 수정 없는 확인 응답 | 유지 | 설명·코멘트만 추가 |
| 문안 수정 포함 확인 응답 | 1 증가 | 한 번의 응답에 대해 1회 증가 |
| 검수자의 문안·파일 수정 | 유지 | 콘텐츠 버전은 별도 증가 가능 |
| 배정 전 취소 후 재제출 | 유지 | 작성 중에서 수정했더라도 취소 경로는 유지 |
| 회수 승인 후 재제출 | 1 증가 | 회수 승인 시점이 아닌 재제출 시점 |
| 승인자의 수정 요청 | 1 증가 | 검수 중으로 돌려보내는 시점 |

자동 저장 횟수, 수정한 콘텐츠 수, 동일 요청의 재시도 횟수를 차수 증가 횟수로 사용하지 않는다. 응답 도중 수정했다가 원래대로 되돌린 경우, 버튼·변수·파일만 수정한 경우를 문안 수정으로 볼지는 추가 협의가 필요하다. 설계 제안은 확인 요청 시점의 대상 버전과 응답 제출 시점의 버전을 비교해 변경 범위와 판단 근거를 남기는 것이다.

### 7.2 충돌하는 행동의 처리

배정과 취소, 확인 요청과 검수 완료, 회수 처리와 검수 완료, 여러 승인자의 동시 처리처럼 하나의 요청 상태를 바꾸는 행동은 동시에 성공해서는 안 된다. 서버의 현재 상태와 대상 버전을 기준으로 하나의 유효한 결과만 반영하고, 뒤늦은 요청에는 변경된 현재 상태를 안내한다.

회수 신청이 남은 상태에서 확인 요청·검수 완료를 허용하는지와 기존 회수 신청을 어떻게 끝낼지는 원문에 명시되지 않았다. 설계 제안은 주담당이 회수 신청을 먼저 종결하도록 제한하는 것이며, 이를 확정 정책으로 취급하지 않는다.

## 8 요청 작성과 콘텐츠 입력

### 8.1 공통 정보

| 항목 | 요구 수준 | 규칙 |
|---|---|---|
| 제목 | 필수 | 요청 식별과 검색에 사용 |
| 유형 | 필수 | 신규 작성 시 활성 유형만 선택 |
| 희망 납기 | 필수 | 요청자가 입력한 값과 확정 납기를 분리하고 원래 값 보존 |
| 목적 | 필수 | 검수 의도를 설명 |
| 대상 고객 | 필수 | 실제 개인정보 수집 요구가 아니라 콘텐츠 대상의 설명 |
| 배경 | 필수 | 검수에 필요한 맥락 |
| 캠페인 | 선택 | 요청과 완료본 검색에 사용. 독립 관리 기능 여부는 별도 결정 |

필수 항목이 비어 있는 작성 중 데이터의 임시 저장 허용 범위와 제출 검증을 구분한다. 저장 중·저장됨·실패를 명확히 표시하고 서버 저장 전에는 성공으로 표시하지 않는다.

요청에 여러 유형의 콘텐츠를 섞을 수 있는지, 요청의 유형 변경을 어느 시점까지 허용하는지는 명시적 결정이 필요하다. 프로토타입의 단일 유형 제한을 계약상 규칙으로 확정하지 않는다.

### 8.2 유형별 입력

| 유형 | 관리할 내용 | 작성 지원 |

### 8.3 길이와 채널 규격

| 구분 | 클라이언트 제시값 | 미확정 내용 |
|---|---|---|

| 문자 | SMS 90바이트, LMS 2,000바이트 | 인코딩, 전환 안내, 초과 시 저장·제출 제한 |
| RCS | 미정 | 유형별 카드·이미지·본문·버튼 규격 |

위 수치는 외부 채널의 최신 규격을 검증한 결과가 아니다. 협의 03에서 규격을 확정하고, SMS에서 LMS로 전환할 때의 안내 채택 여부는 협의 23에서 정한다. 글자 수와 바이트 수, 화면 미리보기와 실제 발송 규격을 구분한다.

## 9 저장과 버전 및 편집 충돌

자동 저장을 기본으로 수동 저장도 제공한다. 요청 공통 정보와 콘텐츠별 저장 내용의 변경을 구분한다. 편집 가능한 역할과 상태를 저장 시점마다 확인하고, 제출 전에 저장 중인 내용과 검수 대상 버전이 일치하도록 처리한다.

문안별 편집 잠금과 저장 버전 비교를 모두 적용한다. 잠금은 동시에 편집하는 상황을 안내하고, 버전 비교는 잠금 만료나 네트워크 장애가 있더라도 다른 사용자의 최신 저장본을 덮어쓰지 못하게 한다. 잠금 만료시간, 연장, 강제 해제 권한과 사유, 재연결·복구 방식은 협의 20에서 확정한다.

충돌 시 서버 최신본을 임의로 덮어쓰거나 내용을 자동 병합하지 않는다. 사용자가 최신본과 자신의 입력을 확인하고 다시 저장할 수 있는 안내가 필요하다. 세부 비교 화면과 선택 방식은 추가 설계 항목이다.

콘텐츠 저장 버전은 검수 차수, 변경자, 변경 시각, 변경 내용, 이전 버전과 연결한다. 파일 수정본도 새 파일 버전으로 저장한다. 자동 저장마다 이력 버전을 만들지, 저장 이벤트와 사용자에게 보여줄 버전을 어떻게 묶을지는 협의 20에서 용량·복구 요구와 함께 결정한다.

제품 내부 탭은 요청과 콘텐츠의 화면 상태를 유지한다. 필터, 활성 콘텐츠, 편집 상태, 교정 결과 위치 등 보존 범위와 동시 탭 수는 미정이다. 미저장 변경이 있는 탭을 종료할 때는 경고한다. 다른 탭의 교정 결과를 선택하면 해당 탭과 문자열 위치로 이동한다.

## 10 첨부파일

### 10.1 등록과 검수 범위

요청당 10개, 파일당 50MB가 제시값이다. 허용 형식은 PDF·DOCX·HWP·XLSX·PPTX·TXT·PNG·JPG이며, 총용량은 미정이다. 서버는 확장자, 실제 파일 형식, 용량을 확인하고 바이러스 검사를 적용한다. 파일명만으로 정상 파일로 판단하지 않는다.

| 파일 종류 | 전체 분량과 실제 검수 범위 단위 |
|---|---|
| PDF·Word·한글 | 페이지 |
| Excel | 행 |
| PPT | 슬라이드 |
| 텍스트 | 줄 |
| 이미지 | 장 |

파일마다 전체 분량과 실제 검수 범위를 구분한다. 업무량에는 실제 검수 범위를 사용하며 서로 다른 단위를 합산하지 않는다. 범위 입력 형식, 불연속 범위, 중복 구간, 전체 분량 초과 검증 방식은 상세 설계에서 확정한다.

### 10.2 처리 상태와 보안

설계 제안으로 업로드 진행, 검사 대기, 검사 중, 사용 가능, 차단, 실패를 구분한다. 이 상태는 요청의 업무 상태와 다르다. 검사 전 파일의 열람·제출·다운로드 허용 여부와 장애 시 처리는 협의 04에서 확정한다. 권장 기본안은 안전성이 확인되지 않은 파일을 업무 완료나 일반 다운로드에 사용하지 않는 것이다.

백신 제품, 검사 비용, 재검사, 실패·탐지 안내, 다운로드 실패·재시도, 임시 파일 정리와 실제 파일 삭제 정책도 같은 협의에 포함한다. 콘텐츠에서 파일을 제거하는 행위가 과거 저장 버전과 완료 원본의 파일까지 삭제하는 것으로 이어져서는 안 된다.

### 10.3 교정과 파일 버전

첨부파일이 하나라도 있는 자유입력형은 교정 버튼과 결과를 비활성화하고 전체 검사에서 제외한다. 기존 교정 결과도 현재 검수 근거로 사용하지 않는다. 첨부를 모두 제거하면 교정을 다시 사용할 수 있다. 첨부 파일 내용을 자동 추출하거나 수정하지 않는다.

## 11 XLSX 대량 등록

대량 등록 대상은 알림톡과 문자다. RCS 또는 자유입력형까지 확장하는 것은 현재 원문에 포함되지 않는다.

| 유형 | 원문에 제시된 열 |
|---|---|
| 알림톡 | 승인템플릿, 본문, 버튼명, 버튼링크 |
| 문자 | 발신자, 본문, 수신거부문구포함 Y 또는 N |

템플릿·샘플 제공, 파일 업로드, 첫 행의 제목을 이용한 열 해석, 행별 검증, 오류 사유 안내, 정상 행 선택·반영을 제공한다. **오류 행이 있다는 이유만으로 정상 행까지 모두 거절하지 않는다.** 복수 버튼 표현과 선택 적용 방식은 양식 확정 시 정한다.

설계 제안은 파일을 읽고 검증한 결과와 실제 콘텐츠 반영을 구분하는 것이다. 원본 행 번호, 유효 여부, 오류 사유, 사용자가 선택한 행, 적용된 콘텐츠를 연결해 부분 성공과 재시도를 설명할 수 있게 한다. 동일 반영 요청을 재시도해도 콘텐츠가 중복 생성되지 않아야 한다.

최대 행 수, 예상·최대 용량, 동시 작업 수, 처리 시간 목표, 비동기 또는 분할 처리 여부, 진행률, 취소·재개·실패 복구는 협의 05에서 정한다. 프로토타입의 500행·5MB 제한과 간소화된 열 구성은 실제 서비스 요구사항이 아니다.

## 12 프로젝트 변수

변수는 프로젝트별 공유 항목이다. 작성 화면에서는 직접 자유 입력하는 대신 현재 프로젝트의 변수를 검색해 선택·삽입한다. 프로젝트 접근 권한이 있는 사용자는 신규 변수를 등록할 수 있고 고객사 관리자가 목록과 사용 상태를 관리한다.

변수 키는 같은 프로젝트 안에서 중복될 수 없고 공백을 허용하지 않는다. 자료형은 텍스트·숫자·날짜·링크이며 등록자, 등록 시각, 변경 이력을 기록한다. 대소문자 구분, 허용 문자, 값 형식, 비활성 변수의 기존 문안 표시, 변수 변경이 기존 콘텐츠에 미치는 영향은 협의 14에서 결정한다.

설계 제안은 콘텐츠가 사용한 변수와 당시 표현을 버전에 연결하는 것이다. 변수 사전이 바뀌어도 완료본의 문안이나 과거 교정 근거가 자동 변경되지 않아야 한다. 미등록 변수 표기가 붙여넣기로 들어온 경우의 안내와 제출 처리도 확정한다.

## 13 규칙 기반 텍스트 교정

### 13.1 필수 구현과 선택 사용

교정 실행 기능 자체는 1차 필수 개발이다. 사용자는 교정 없이 검수 요청과 검수 완료를 할 수 있다. 가이드 열람과 체크리스트 완료도 다음 단계의 필수 조건이 아니다.

고객사와 콘텐츠 유형의 조합에 배정된 유효 데이터셋으로 탐지 표현과 대체 표현을 검사한다. 요청자는 작성·응답 중, 배정 검수자는 검수 중인 편집 가능 범위에서 사용한다. 여러 문안에는 전체 검사를 제공하고 문안별 결과 카드를 표시한다.

### 13.2 결과의 유효성

교정 실행은 대상 콘텐츠와 버전, 사용 데이터셋과 기준 버전, 실행자와 시각, 대상 문자열 위치, 검출 내용과 대체 제안에 연결되어야 한다. 문안·변수·연결값이 바뀌면 기존 결과를 최신 내용과 불일치로 표시한다. 검사 완료 후 데이터가 바뀌었는데도 새 문안의 검사 결과처럼 보여서는 안 된다.

결과 선택 시 대상 콘텐츠와 문자열 위치로 이동한다. 위치 표현 방식, 문자열 반복, 여러 규칙의 중첩, 교정 결과 상태와 치환 적용 방식은 엔진 명세에 맞춰 정의한다. 데이터셋 변경에 따른 재검사 표시 정책도 협의가 필요하다.

### 13.3 제공 자료와 책임

와이어링크는 교정 엔진의 동작 명세, 유형별 시드, 기대 결과를 제공할 예정이다. **이는 실행 가능한 엔진이나 연동 API가 이미 제공된다는 뜻이 아니다.** 실행 모듈을 개발사가 구현하는지, 별도 제공 엔진을 연결하는지, 장애·성능과 기준 해석을 누가 책임지는지 협의 15에서 확정해야 한다.

1차 운영 담당자는 고객사 × 유형별 유효 데이터셋을 배정·연결·확인한다. 유효 데이터 저장 구조와 시드도 1차다. 기준 편집·충돌 검사·배포 비교·복원 관리 화면까지 1차로 확장하지 않는다. 후속에는 변경 불가 배포 묶음, 과거 기준의 새 버전 복원, 배포 묶음과 연결된 기준 변경 공지가 포함된다.

## 14 검수와 승인

### 14.1 검수 배정

대표 검수자가 한 명 이상의 검수자를 배정하고 그중 정확히 한 명을 주담당으로 지정한다. 공동 검수자가 별도의 부분 완료 상태를 만들지 않는다. 검수 중에는 사유와 인수인계 내용으로 담당자와 주담당을 바꿀 수 있지만, 확인 요청·승인 대기·최종 완료에서는 바꿀 수 없다.

배정 검수자는 검수 중일 때 문안·파일 편집, 검수 의견, 콘텐츠를 지정한 확인 요청을 할 수 있다. 확인 요청이 발생하면 요청 전체가 중단된다. 주담당만 공동 결과와 대상 버전을 확인하고 요청 전체의 검수를 완료한다.

### 14.2 확인 요청과 회수

질문과 답변은 대상 콘텐츠 및 버전과 연결하고 요청 통합 이력에서도 보여 준다. 같은 차수에서 질문과 답변을 여러 번 반복할 수 있다. 동시에 여러 질문을 보낸 경우 답변의 완료 단위와 요청 재개 조건은 상세 협의가 필요하다.

회수는 요청자의 신청, 주담당의 결정, 사유·의견·결과와 기존 배정 이력을 보존한다. 승인하면 작성 중으로 돌아가고 활성 배정을 해제한다. 거절하면 검수 중과 기존 배정을 유지한다. 회수 승인 후에는 과거 참여자의 현재 조회 권한도 작성 중 제한에 맞춰 재평가한다.

### 14.3 승인 큐와 적격성

승인자는 요청별로 지정하지 않고 프로젝트 공용 승인 대기 목록을 사용한다. 적격 승인자 한 명이 처리하면 충분하며 전원 합의를 요구하지 않는다. 해당 요청의 요청자·배정 검수자·주담당은 승인자 역할을 갖고 있어도 승인할 수 없다. 이전에 배정되었다가 해제된 검수자까지 금지 대상에 포함할지는 별도로 결정한다.

활성 승인자가 없으면 승인 대기로 전환하지 않는다. 고객사 관리자에게 승인자 지정을 요청하고 요청자·대표 검수자에게 지연을 알린다. 임시 승인 위임은 제공하지 않는다. 활성 승인자는 있지만 모두 해당 요청에 부적격인 경우도 같은 절차를 적용할지는 협의 19의 미정 항목이다. 설계 권장안은 이 경우에도 전환을 막아 처리 불가능한 승인 대기를 만들지 않는 것이다.

### 14.4 승인 대상 고정

승인 대기에 들어가면 검토할 콘텐츠 버전과 배정 검수자·주담당을 고정한다. 확정 납기와 긴급도는 승인자만 바꿀 수 있고 사유·전후 값을 기록한다. 수정 요청은 이유·위치·기대 내용을 기록하고 기존 배정으로 검수 중에 복귀시키며 차수를 한 번 증가시킨다. 재검수 후 승인 대기에 다시 들어오면 새 대상 버전을 확인하게 한다.

## 15 완료본과 검색 및 반출

### 15.1 완료 묶음

최종 완료 시 요청, 모든 대상 콘텐츠와 정확한 버전, 최종 파일과 버전, 완료 상태·시각·행위자를 고정한다. 최신 편집 데이터나 현재 데이터셋을 따라가는 참조만으로 완료본을 구성하지 않는다. 어떤 구현을 선택하든 과거 완료 당시 내용을 재현할 수 있어야 한다.

완료 후 문안·파일·납기·긴급도를 직접 수정하지 않는다. 원본과 연결된 새 작성 중 요청으로 후속 작업을 시작한다. 최신 완료본을 기본으로 보여 주고 과거 완료본과 후속 요청을 펼쳐 볼 수 있어야 한다. 후속 요청 분기와 최신 완료본을 선택하는 기준은 상세 설계에서 정한다.

### 15.2 검색

| 검색 영역 | 조건 |
|---|---|
| 요청 목록 | 제목, 요청 ID, 유형, 상태, 대표 검수자, 주담당, 배정 검수자, 확정 납기, 접수일 |
| 완료 콘텐츠 | 문안, 파일명, 본문, 완료일, 요청 상태, 유형, 캠페인 |

검색과 결과 개수에도 작성 중 제한과 고객사·프로젝트 권한을 먼저 적용한다. 파일명 검색이 첨부 내부 본문 검색을 뜻하지는 않는다. OCR·본문 추출은 현재 범위 밖이다. 공개·비공개 보관 정책은 후속 기능이다.

### 15.3 완료 원본 반출

문안은 개별 복사와 요청 전체 XLSX 내보내기를 제공한다. 기본 항목은 다음 10개다.

| 순번 | 항목 | 상세 결정 사항 |
|---|---|---|
| 1 | 콘텐츠 식별자 | 외부 표시 ID와 형식 |
| 2 | 유형 | 표시 명칭 |
| 3 | 제목 | 요청 제목과 콘텐츠 제목 구분 |
| 4 | 본문 | 줄바꿈과 문자 보존 |
| 5 | 버튼명 | 복수 버튼 표현 |
| 6 | 연결값 | 버튼과 연결값 대응 |
| 7 | 변수 | 복수 변수와 표현 형식 |
| 8 | 완료 버전 | 버전 표시 형식 |
| 9 | 요청 완료 상태 | 승인 사용 여부에 맞는 최종 상태 |
| 10 | 완료일 | 시각 포함 여부와 KST 표시 |

이 순서는 설명용 기준이며 최종 열 이름·순서·자료형은 협의 06의 샘플 확인으로 확정한다. 실제 XLSX 생성·다운로드는 1차다. 첨부는 최종 파일과 파일별 완료 버전 명세를 묶음으로 제공한다.

설계 제안은 반출 요청 시점뿐 아니라 결과 파일 취득 시점에도 권한과 완료 버전을 확인하고, 생성·실패·다운로드 이벤트를 구분하는 것이다. 파일 생성 실패, 재시도, 링크 유효기간과 보관·정리 방식은 협의 04·06에서 확정한다.

## 16 납기와 업무량 및 실적

희망 납기는 원래 값을 보존하고 확정 납기·긴급도와 분리한다. 납기·긴급도 변경에는 사유, 이전 값, 이후 값, 행위자와 시각이 필요하다. 고객사별 변경 권한을 어느 수준까지 설정할지는 협의 18에서 결정한다.

납기 임박은 D-3 이내가 현재 기준이다. 달력일·영업일, 하루의 마감 시각, 지연과 임박의 중복 표시, 고객사 설정 변경의 적용 시점은 협의 08에서 정한다. 화면의 임의 기준일을 실서비스 집계에 사용하지 않는다.

| 지표 | 현재 기준 | 미확정 사항 |
|---|---|---|
| 현재 업무량 | 배정 대기·검수 중·확인 요청·승인 대기 | 역할별 합산 범위와 공동 검수자 표시 |
| 문안 글자 수 | 변수 치환 전 원문, 공백 포함 | 제목·버튼·줄바꿈 포함 여부 |
| 파일 검수량 | 실제 검수 범위, 단위별 표시 | 범위 입력과 중복 구간 처리 |
| 조직 실적 | 고유 요청 수와 콘텐츠 수 분리 | 취소·회수·재접수·공동 검수 중복 처리 |
| 접수 집단 완료율 | 조회 기간 접수 요청을 분모로 사용 | 분자, 측정 시점, 최초·최근 접수 기준, 분모 0 |
| 기간 내 완료량 | 해당 기간에 완료된 업무 | 완료율 분자와 동일 개념으로 취급하지 않음 |
| 개인 실적 | 검수 완료 실적과 배정·관리 실적 구분 | 귀속 시점, 주담당·공동 검수자 배분 방식 |

조회 기간은 접수일 기준 KST 00:00 경계를 사용한다. 설계 제안은 저장 시각을 일관되게 관리하고, 조회 구간은 시작 이상·종료 다음 날 미만으로 해석해 경계 중복을 방지하는 것이다. 실제 완료율의 분자와 재접수 규칙은 협의 09의 결정 전에는 확정하지 않는다.

## 17 알림과 공지

### 17.1 업무 알림 대상

| 업무 사건 | 대상 |
|---|---|
| 신규 제출 | 프로젝트 대표 검수자 |
| 배정·변경 | 요청자, 추가·해제된 검수자 |
| 확인 요청 | 요청자 |
| 확인 응답 | 담당 검수자 |
| 회수 신청 | 주담당에게 처리 요청, 다른 배정 검수자·대표 검수자에게 사유 |
| 회수 처리 | 요청자·배정 검수자·대표 검수자 |
| 승인 미사용 검수 완료 | 요청자 |
| 승인 사용 검수 완료 | 해당 요청의 적격 프로젝트 승인자 전원 |
| 승인 완료·수정 요청 | 요청자와 검수자 |
| 납기 변경 | 요청자·대표 검수자·담당 검수자 |
| 활성 승인자 부재 | 고객사 관리자에게 지정 요청, 요청자·대표 검수자에게 지연 안내 |

행동 수행자는 제외하고 중복 대상은 한 번만 알린다. 관리자라는 이유로 모든 알림을 보내지 않고 다음 행동 책임자일 때만 포함한다. 알림 읽음과 업무 완료는 별도로 관리한다.

납기 임박 재통지의 제시 기준은 1·2회차 인앱, 3회차 인앱과 이메일이다. **일반 미처리 알림에 같은 채널 규칙을 적용할지는 미정**이다. 최초 통지를 횟수에 포함하는지, 간격, 중단·재시작, 납기 변경 시 횟수 초기화, 고객사별 설정은 협의 10에서 결정한다.

설계 제안으로 업무 저장 성공과 알림 발송을 분리하되, 발송 대상 작업이 누락되지 않게 연결 기록을 남긴다. 메일 장애가 이미 완료된 승인을 되돌리거나, 재시도가 동일 알림을 여러 번 만드는 구조를 피한다. 발송 대기 중 권한이 사라진 수신자에게 원문을 보내지 않는 정책도 정의한다.

### 17.2 공지

고객사 관리자는 프로젝트 공지와 고객사 전체 공지를 작성·수정·철회하며 즉시 게시한다. 고객사 전체 공지는 해당 고객사의 전체 구성원에게 노출하고 프로젝트·역할 필터로 제한하지 않는다. 다른 고객사에서는 목록·검색·상세·알림으로 볼 수 없다.

상위 범위 공지를 하위 권한으로 수정하지 못하게 하고 수정·철회 이력을 보존한다. 예약 게시의 1차 포함 여부와 변경·철회 방식은 협의 11에서 결정한다. 솔루션 운영 담당자의 공통 운영·기준 변경 공지는 후속이며, 기준 변경 공지만 실제 배포 묶음과 적용 시점에 연결한다.

## 18 관리와 초기 운영

### 18.1 고객사 관리자의 업무

프로젝트 생성·수정·사용 상태·대표 검수자·참여 범위, 사용자 초대·비활성화·역할·인수인계, 변수 목록·사용 상태, 고객사 운영 설정과 공지를 관리한다. 고객사명·알림 채널·납기 임박 기준은 관리 항목이며, 도메인과 승인 사용 여부는 읽기 전용이다. 항목별 수정 권한과 기본값은 협의 12에서 확정한다.

### 18.2 솔루션 운영 담당자의 업무

고객사 생성·목록·상세·비활성, 초기 프로젝트·사용자·권한 설정, 콘텐츠 유형의 활성·비활성, 고객사 × 유형별 유효 데이터셋 연결, 샘플 요청·콘텐츠와 교정 규칙 시드 운영을 제공한다. 유형을 비활성화해도 과거 요청을 새 유형으로 자동 변환하지 않는다.

고객사의 물리 삭제는 1차 범위 밖이다. 이력과 연결된 고객사·프로젝트·사용자는 비활성화하여 보존한다. 비활성 고객사의 로그인·열람·다운로드 허용 수준과 복구 절차는 협의 22에서 확정한다.

### 18.3 인수인계와 비활성화

조직·권한 변경 전 진행 요청, 주담당 여부, 질문 대기, 승인자 공백, 편집 잠금과 발송 대기 알림에 미치는 영향을 확인한다. 담당자만 바꾸고 책임 기록을 지우지 않는다.

승인 대기·확인 요청에서는 검수자 변경이 금지되지만, 구성원 제외 전 인수인계를 완료해야 한다. 이 두 규칙이 충돌하는 경우의 처리 순서, 업무 복귀 여부, 비활성화 유예와 예외 승인 주체는 미정이다. 새 상태나 관리자 강제 승인 기능을 임의로 만들지 않는다.

### 18.4 시드와 데모 데이터

교정 기준 등 제품 동작에 필요한 초기 데이터와 시연용 요청·콘텐츠를 구분한다. 샘플 초기화가 실제 운영 요청·완료본·이력을 삭제하지 않도록 분리한다. 대상 고객사·프로젝트, 실행자, 실행 결과와 영향 범위를 기록한다. 분리 방식과 초기화 범위는 협의 22에서 정하며, 운영 데이터가 있는 환경에서 무조건 전체 초기화하는 기능은 만들지 않는다.

### 21.2 핵심 관계

요청은 여러 콘텐츠를 갖고 콘텐츠는 여러 버전을 갖는다. 하나의 검수 차수 동안 여러 콘텐츠 버전이 저장될 수 있다. 배정은 사용자와 요청의 다대다 관계이며 주담당 지정과 배정 변경 이력을 포함한다. 승인자는 요청 담당자 관계 대신 프로젝트 역할을 통해 결정하지만, 실제 승인 행위는 해당 사용자와 대상 버전에 고정한다.

완료 묶음은 완료 당시 콘텐츠·파일 버전을 연결한다. 새 후속 요청은 완료 묶음을 원본으로 연결하며 원본을 수정하지 않는다. 교정 실행은 실행 당시 문안과 데이터셋 버전을 각각 연결한다. 사용자의 현재 역할과 과거 업무를 수행했을 당시의 책임 기록을 같은 값으로 덮어쓰지 않는다.

### 21.3 데이터 무결성

고객사 경계가 다른 프로젝트·요청·콘텐츠·파일을 서로 연결할 수 없어야 한다. 배정된 검수자와 주담당은 해당 프로젝트에서 유효해야 하며 주담당은 반드시 배정 집합에 포함된다. 같은 프로젝트의 변수 키는 중복될 수 없고 고객사 × 유형 조합에는 하나의 유효 교정 기준을 연결한다.

동일 제출, 동일 상태 전환, 동일 차수 증가, 동일 완료 묶음 생성의 재시도로 중복 결과를 만들지 않는다. 승인 대기와 완료에 연결된 버전은 이후 저장으로 바뀌지 않는다. 비활성화가 과거 이력과 최종본의 참조를 끊지 않아야 한다.

### 21.4 조회와 보존 설계

고객사·프로젝트와 상태·담당자·납기·접수일·완료일을 조합한 조회가 주요 접근이다. 요청별 통합 이력, 콘텐츠별 버전, 미처리 작업, 고객사 × 유형별 기준도 빈번히 조회한다. 이를 기준으로 물리 설계에서 인덱스와 검색 방식을 정하되 예상 건수 없이 특정 기술이나 분리 구조를 확정하지 않는다.

본문·첨부·교정 결과·버전·로그는 증가량이 다르므로 각각 용량 산정이 필요하다. 업무 이력 무삭제 보존과 접근·반출 로그 보존 정책을 구분한다. 원문에 있는 ‘3년까지 허용’을 모든 로그의 3년 자동 삭제 요구로 해석하지 않는다.

## 23 운영 요구와 비기능 범위

### 23.1 운영 규모

고객사 수, 고객사당 사용자 수, 동시 접속·동시 편집 수, 일일 요청·콘텐츠 수, 콘텐츠당 평균 버전 수, 첨부 평균·최대 용량, XLSX 행 수, 교정 동시 실행량, 검색 범위와 로그 증가량을 확인한다. 아직 정해지지 않은 수치를 확정 성능 보장으로 약속하지 않는다.

가견적에는 예상 규모와 최대 규모 가정, 주요 화면·저장·검색·교정·일괄 작업의 응답 목표, 지원 브라우저를 명시한다. 운영 환경과 검증 환경의 규모 차이도 구분한다. 이 조건은 협의 21의 대상이다.

### 23.2 보안과 운영 책임

서버 권한 검증과 고객사 격리를 모든 처리에 적용한다. 인증 정보, 초대 정보, 고객사 원문이 불필요한 오류 기록이나 외부 알림에 노출되지 않게 한다. 파일 검사, 안전한 파일 취득, 세션 종료·권한 회수, 운영자의 제한 접근과 감사 기록이 필요하다. 구체적인 보안 제품·인증 기준을 원문에 없는 계약 요구로 추가하지 않는다.

### 23.3 복구와 모니터링

백업 대상에는 업무 데이터뿐 아니라 파일 원본, 완료 묶음, 기준 데이터, 필요한 설정을 포함하는 방안을 검토한다. 허용 데이터 손실과 복구 시간 목표, 백업 주기·보관·복원 책임은 미정이다. 데이터베이스와 파일 버전이 서로 다른 시점으로 복구되어 완료 묶음이 깨지지 않도록 일관성 기준을 정한다.

설계 제안으로 로그인·저장·상태 전환 실패, 파일 검사 실패, 알림 미전달, 일괄 처리 지연, 교정 오류, 권한 거부와 운영자 접근을 확인할 수 있는 운영 기록을 마련한다. 알림 받을 운영자와 장애 대응 범위는 유지보수 조건에 포함한다.

| 현재 상태 중심의 실적 예시 | 합의된 접수·완료·재접수·기여도 기준에 따른 집계 |
| 체험용 고객사 전환·접근 권한 부여 | 계정 소속과 승인된 운영 접근만 허용 |
| 관리자 화면의 교정 기준 체험 | 원문 기준의 솔루션 운영 담당자 배정 권한 적용 |
| 화면에 열람 가능한 99개 기능 | 기능명세 목록의 존재와 실제 기능 구현 완료는 별개 |

프로토타입이 지원하지 않는 세부 행동도 원문 1차 요청이면 본 개발에서 구현해야 한다. 반대로 프로토타입에 임시로 있는 동작·수치·단순화는 자동으로 계약 범위나 업무 규칙이 되지 않는다.

## 25 개발 순서와 의존성

### 25.1 요구사항과 설계 기준 확정

교정 엔진 책임과 시드, 고객사별 정책 설정 범위, 파일 보안 처리, 채널 규격, 운영 규모, 계정 소속 범위, 미정 상태 예외를 우선 결정한다. 1차·후속 분류 조정과 구현 수준의 변경은 기능 ID와 협의 번호에 기록한다.

### 25.2 공통 기반

고객사·프로젝트·계정·소속·역할과 제한 접근을 구성하고 실제 로그인·초대·세션을 연결한다. 공통 권한 판단과 업무 이력의 기록 기준이 이후 모듈의 기반이 된다.

### 25.3 작성과 검수

요청·콘텐츠·버전·변수·저장 충돌을 구성하고 제출·배정·확인·취소·회수·차수를 연결한다. 첨부, XLSX, 교정은 각각의 명세와 운영 조건을 기반으로 연결한다. 저장 구조가 확정되기 전에 화면 임시 객체를 그대로 데이터베이스로 옮기지 않는다.

### 25.4 승인과 완료 데이터

승인 적격성과 대상 버전 고정, 수정 요청·재검수, 완료 묶음, 원본·후속 연결, 완료 검색과 실제 반출을 연결한다. 완료 데이터를 정확히 고정한 후 실적과 재사용 기능을 확장한다.

### 25.5 업무 운영과 인수

알림·재통지, 고객사 공지, 납기·실적, 계정 변경과 인수인계, 초기 설정·시드, 운영 이력과 복구를 연결한다. 사용자 흐름이 모두 연결된 상태에서 합의된 규모와 환경을 기준으로 완료를 판단한다.

10월 말 시연은 목표일이며 확정 납기나 90개 전체 완료 약속이 아니다. 상세 일정과 투입 인력은 의존 자료 수령일, 결정 완료일, 구현 수준을 반영해 산정한다. 시연 범위를 줄이는 경우에도 실제 제품의 1차 요청 범위를 자동 축소한 것으로 처리하지 않는다.

## 27 납품과 변경 관리

기본 납품 범위는 합의된 기능이 연결된 운영 제품과 실제 로그인·권한·저장·업무 처리·검색·반출이다. 소스코드, 데이터베이스 구조, 서버 연동 명세, 배포·운영 문서, 초기 기준 데이터와 환경 구성, 데이터·소스 소유 관계의 제공 범위를 계약에서 명시한다.

프런트엔드 개발, UI 디자인·퍼블리싱, 구현 후 화면 보완의 범위와 비용을 구분한다. 외부 서비스 이용료, 파일 저장·검사, 메일·운영 비용과 유지보수 범위·장애 대응 조건도 분리해 제시한다. 1차 90개와 후속 9개는 별도로 산정하며 공통 기반 작업의 공수를 여러 기능에 중복 기재하지 않는다.

변경 요청에는 관련 기능 ID, 현재 요구와 바뀌는 내용, 업무 규칙·권한·데이터·화면·운영 영향, 비용·일정 영향, 결정자·결정일·근거를 남긴다. 회신이나 침묵을 합의로 간주하지 않는다. 기능명세 회신란과 기획서가 서로 다른 규칙을 갖지 않도록 같은 결정으로 갱신한다.
